The Core Agent Loop

An agent is a model calling tools in a loop until the task is complete. It fits on an index card, and every later chapter is built on top of it.

01Chapter in 60 seconds

  • The danger of a small primitive: it invites you to bolt features on before the core is sound.
  • The one edge that matters: observation → reasoning. Without it you have a chain.
  • Get this loop wrong (no verification, no budget, observations discarded) and nothing above it is reliable.

02Observe, reason, act, observe

A closed feedback loop: observe the environment, reason about the next move, act, observe the new state. Repeat until a termination condition fires.

Key insight

A test failure is new context the model did not have before. The loop's whole value comes from feeding it into the next reasoning step instead of discarding it.

Why it beats one-shot: reasoning-only and acting-only agents both underperform the interleaved version, because each step is conditioned on a real observation.

04Plan-and-execute vs reactive loops

Pitfall

Plan-and-execute can over-commit to a bad plan. If step two shows the plan is wrong, revise it; don't push through the rest. A plan-and-execute loop with no replanning is a chain wearing a loop's clothing.

DimensionPlan-and-executeReactive
Decision granularityFull multi-step plan up frontOne next action at a time
Best forOrdered, interdependent tasks (migrations, multi-file features)Open-ended exploration (debugging, unfamiliar APIs)
Failure modeOver-commits to a wrong planWanders without global direction
RecoveryNeeds an explicit replanning triggerNaturally re-decides each step
Token costHigher up front, lower per stepLower up front, can drift higher
ObservabilityThe plan is an auditable artifactIntent is implicit in the trace
Rule

Neither dominates. Mature loops often start reactive and promote to plan-and-execute once the task structure is understood.

05The agent loop as a state machine

A set of states, transitions between them, and one or more terminal states.

States

  • planning
  • gathering context
  • executing a tool call
  • awaiting tool result
  • reasoning over a result
  • awaiting human input

Transitions = events

  • a tool call returns
  • a verifier passes or fails
  • a budget is exhausted
  • a human approves or rejects

Terminal: few, explicit

  • SUCCEEDED: verified completion
  • BLOCKED: needs a human (credentials, judgement call, vetoed action)
  • FAILED: retries or budget exhausted
Gap a state machine exposesWhat it looks like in production
State with no exit transitionThe loop hangs
Transition with no clear triggerBehaviour nobody can explain from the log
Terminal state unreachable from a branchThat path can never legitimately stop
  • Why not a while-loop with ifs? There the state hides in local variables; you must read the whole function to know if it can terminate.
  • Few terminal states: the caller knows to retry, escalate or alert. "Partially done" or "done but unsure" pushes ambiguity onto every consumer.
  • LoopState.transition_to records every edge, so a finished run carries its own audit trail.

06Two nested loops

From the field

Newcomers "optimise the loop" by changing temperature or top-p. That only touches the inner loop. Tune the architecture before tuning the sampler.

07Synchronous vs asynchronous execution

SynchronousAsynchronous
How it runsCaller blocks until each iteration finishesRuns in the background; caller is notified, polls, or is interrupted
Needed whenInteractive sessions, first buildsLonger than a session tolerates, or on a schedule with no human (Ch 11)
DebuggingEasy: a hang reproduces on the spotHard: it failed three hours ago, in the background
AddsNothing extraDurable, resumable state · idempotent actions · out-of-band notification
Best practice

Start every new agentic system synchronous, even if the end state is event-driven. Move to async only once the sync version is reliable. The real cost of async is the state and idempotency discipline, not the concurrency primitives.

08The loop driver: AgentLoop.run

About 120 lines. What matters is that every stop is a named decision and every transition is observable.

while not state.phase.is_terminal:
    terminal = self.policy.check_terminal(state)        # 1) gate FIRST (Ch 3)
    if terminal: state.transition_to(*terminal); break
    state.iteration += 1
    response = self.llm.complete(state.messages, tools=self.tools.schemas())  # 2) reason
    if not response.wants_tool:                           # 3a) final answer
        if self._verify(state): return SUCCEEDED          # verify BEFORE success
        self._record_no_progress(state); continue          # failure becomes context
    for call in response.tool_calls:                      # 3b) action path
        if veto := self.policy.veto_action(state, call.name, call.arguments):
            return BLOCKED
        result = self.tools.invoke(call.name, call.arguments)          # ACTING
        state.add_message("tool", result.render(), tool_call_id=call.id)  # OBSERVING

Condensed from loop_engineering_lab/core/agent_loop.py

Best practice

The control gate is the first thing in the loop body, before the model is consulted. Checking budgets before a model call stops the loop from making one extra expensive call past its ceiling on every run.

Why verify first

The model saying "done" is a claim, not a fact. If success keys off a final answer, the loop terminates on confident-but-wrong output, and nothing downstream catches it.

10Self-test: exercises 2.1–2.10

Answer aloud first, then open the card.

2.1The core agent loop in one sentence, then each part?Reason, act, observe.
A model calling tools in a loop until the task is complete. Reason over the message history to pick the next action; act by dispatching the tool call; observe by appending the result to history. Repeat until a termination condition fires or a final answer passes verification.
2.2Why an explicit state machine instead of a while-loop with ifs?Make bugs structurally visible.
  • Exposes phases with no exit (hangs) and terminal states unreachable from a branch.
  • Gives one place to log every transition: replay and debugging.
  • With ad-hoc ifs, state hides in local variables and control flow.
2.3Token-generation loop vs step-orchestration loop: why does it matter?Where is the leverage?
Inner: the model's own token-by-token decoding, which you don't design. Outer: which tool, what context, when to stop, which you do design. Tuning temperature or top-p only touches the inner loop; reliability, cost and correctness live in the outer one.
2.4When plan-and-execute over reactive, and how to prevent over-commitment?Ordered, compounding tasks.
When order matters and early mistakes compound: a multi-file feature, a migration, an interdependent refactor. Add a replanning trigger: after each step, check that reality still matches the plan's assumptions; if not, regenerate the remaining plan.
2.5Why verify before transitioning to success? Where is it in code?"Done" is a claim.
The model declaring done is a claim; verify against tests, a checker or a schema. A failed check becomes new context instead of a silent stop. In AgentLoop.run, the final-answer branch calls self._verify(state) and only then moves to SUCCEEDED; otherwise it records no-progress and continues.
2.6The terminal states, and why keep them few?Three.
SUCCEEDED (verified), BLOCKED (needs a human), FAILED (retries or budget exhausted). Few and explicit tells every caller whether to retry, escalate or alert. "Partially done" states push ambiguity onto consumers and cause multi-agent integration bugs.
2.7An agent loop hangs and never returns. Diagnose.Transition log; tool timeouts.
  • Read the transition log: which phase is it stuck in?
  • Oscillating REASONING ↔ ACTING → misconfigured no-progress detector or tool-call budget.
  • Stuck in ACTING → a tool (HTTP, subprocess) with no timeout: the most common cause.
  • Fix: gate first in the loop body, hard timeout on every tool, no-progress counter that can drive BLOCKED.
2.8What is ReAct, and why beat one-shot generation?Conditioning on real observations.
Interleave reasoning steps with actions. Each action yields an observation the model didn't have, so the next reasoning step is grounded in real feedback. One-shot generation must get everything right blind. Reasoning-only and acting-only both underperform the interleaved version.
2.9Sync vs async: how do you decide, and what changes?What async forces on you.
Build sync first; go async only when runs outlast a session or run on a schedule with no human. Async adds durable, resumable state; idempotent actions (retries don't double side effects); and out-of-band notification.
2.10How do you test the loop without paying for model calls?Dependency inversion.
Depend on an LLMClient protocol with one complete method. Production injects a real adapter; tests inject a deterministic MockLLM (a queue of responses or a policy(messages) function). Then test "budget stops at 3 tool calls" or "failing verifier keeps looping" offline, for free, deterministically.

11Chapter summary

  1. The core loop is observe, reason, act, observe again, repeated until termination.
  2. ReAct interleaves explicit reasoning with action instead of one-shot output.
  3. Plan-and-execute suits ordered, interdependent tasks; reactive suits exploration. Both need a way to recover from a wrong initial assumption.
  4. A formal state machine surfaces missing transitions and unreachable terminal states before they cause incidents.
  5. The token loop (inside the model) and the orchestration loop (around it) are different; loop engineering designs only the outer one.
  6. Build synchronously first; go async only once the loop is reliable.
