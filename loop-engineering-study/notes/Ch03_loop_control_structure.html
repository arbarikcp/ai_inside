Loop Control Structures

A loop that cannot stop is not autonomous. It is expensive. This chapter covers what decides whether the next iteration happens, and what happens when it does not.

01Chapter in 60 seconds

3 a.m.

The most expensive run is not the one that fails. It is the one on its 400th attempt at a test that cannot pass, burning money with nobody watching. It did everything you told it. You never told it when to quit.

02Termination conditions

Every loop needs a concrete, evaluable definition of "done". Three categories:

Vague goal: infinite loop or meaningless output"Improve the dashboard."
Checkable goal: scope + behaviour + constraint"Reduce initial dashboard load time by deferring non-critical charts while keeping existing filters working."

03Stopping rules as first-class design requirements

Best practice

Write termination and failure conditions before any loop logic. "All tests pass and lint is clean" can be checked by code. "The code looks good" is a wish.

GuardStops when the next step would…
Destructive-actionrun an irreversible command (DB drop, force-push, credential rotation) without explicit human approval of that specific action
Scope-creeptouch files or systems outside the defined task boundary, even if the agent thinks it helps
Blocker escalationneed missing credentials, missing data, or a product judgement call the agent has no basis for
Unrelated-changeoverwrite changes a human or another agent made concurrently

Each one is a specific, codifiable veto on the next action, and each maps to a real incident class.

04Loop budgets

A budget is a hard ceiling, independent of whether the loop believes it is making progress.

BudgetProtects againstSignal on exhaustion → fix
IterationPathological retry loopsStrategy is wrong; escalate
TokenContext bloat, runaway costCompaction or summarisation needed (Ch 4)
Tool-callThrashing on a stuck sub-taskAction space or verifier is inadequate
Time (wall-clock)Hanging tools, SLAsA dependency is slow or down
Cost (USD)Cross-model routing surprisesRoute to a cheaper model, or stop
Key insight

An exhausted budget without progress is a signal, not just a limit: the current strategy is wrong. Escalate or switch strategy; don't quietly raise the ceiling and retry. Which budget you hit tells you which subsystem to fix.

Fires onA counter crossing its maxN consecutive iterations with no new information: same error, same failing tests, near-identical action

Progress meansA change in the verifier's output or the set of failing tests, not the model merely saying something different

05Early-exit and short-circuit logic

Exit early when (verified)
  • The success condition is met well before the budget
  • An observation makes the rest of the plan provably unnecessary (the bug doesn't exist in this version)
  • A hard blocker is detected, with no value in workarounds
Never exit early on
  • The model's self-assessment alone ("I think I'm done")
  • That reintroduces confidently wrong output, the failure verification exists to prevent

Early exit and verification are complementary: exit on a checker passing or a deterministic precondition failing.

06Recursive vs iterative structures

Example: while building a feature, the parent needs to know why one library function behaves oddly. A sub-agent investigates just that, keeping the parent's context clean. Cost of recursion: coordination and context passing. Anti-pattern: recursing for trivially coupled steps.

07Nested loops

Pitfall

One budget and one stopping rule for both layers. Result: the system gives up on the whole goal because one inner step failed, or inner thrashing never bubbles up to the outer budget.

Nesting is the load-bearing idea behind "loop stacking", developed fully in Chapter 12.

08Loop re-entry and resumability

1 · Serialise state

What was tried, what succeeded, what is pending, written to durable storage at every iteration boundary, not only at the end.

2 · Resumption protocol

A clear procedure that rebuilds the loop's working memory from that serialised state.

3 · Idempotent actions

Side effects keyed by a deterministic request id, so a repeat is a no-op (Ch 6).

From the field

The most common production failure in long-running loops is not a bad model decision. It is a crash mid-iteration with no durable record, then a restart that redoes a half-finished action. For any loop longer than a few minutes, resumability is a prerequisite.

09Policy in code: TerminationPolicy

Control logic is a separate, testable object, not ifs buried in the loop body. You can unit-test "does the budget stop at five tool calls?" without a model.

@dataclass
class Budget:                       # hard ceiling, independent of perceived progress
    max_iterations: int = 12
    max_tokens: int = 100_000
    max_tool_calls: int = 40
    max_seconds: float = 300.0

    def exceeded(self, state) -> str | None:
        if state.iteration >= self.max_iterations: return "iteration budget exhausted"
        if state.tokens_used >= self.max_tokens:   return "token budget exhausted"
        ...                                       # tool calls, seconds
        return None

def destructive_action_guard(dangerous=None):
    dangerous = dangerous or {"drop_table", "force_push", "rotate_credentials"}
    def rule(state, tool_name, args):
        approved = state.scratchpad.get("human_approved", set())   # only a human step writes this
        if tool_name in dangerous and tool_name not in approved:
            return f"destructive action '{tool_name}' requires human approval"
        return None
    return rule

Un-bypassable guard · 1

Consulted on the action path for every tool call, before dispatch.

Un-bypassable guard · 2

Fails closed: no approval means block.

Un-bypassable guard · 3

Per-action, out-of-band approval: approving one drop_table doesn't approve the next, and the model can't approve itself by writing "I have approval".

Pitfall

A stopping rule that only logs a violation is theatre. policy.veto_action returns a reason before the tool runs, and any reason moves the loop straight to BLOCKED. A guard that fires after the irreversible command has run is not a guard.

11Self-test: exercises 3.1–3.10

Answer aloud first, then open the card.

3.1Why design termination conditions before action logic?"Done" must be observable.
Without an evaluable "done", a loop runs forever or stops on a meaningless heuristic. Asking "what observable signal means success?" first often reshapes the whole design. Stopping rules added last give a system that can act but cannot reliably stop: runaway cost and confidently wrong output.
3.2Stopping-rule categories beyond success/failure?Four guards.
Destructive-action, scope-creep, blocker-escalation and unrelated-change guards. Each is a codifiable veto on the next action and maps to a real incident class.
3.3Tool-call budget exhausted without converging. Just a stop?It's evidence.
No: it's a signal the strategy is wrong (inadequate action space, unusable verifier, or mis-scoped task). Escalate or switch strategy; don't raise the ceiling. Token budget → context bloat; time → slow/hung dependency; tool-call → thrashing.
3.4How do you set budget values for a coding agent?Use the eval distribution.
  • Run on a representative task set; look at iteration and token histograms of successful runs.
  • Set the ceiling just above p95, below where a stuck loop wastes real money.
  • If successes take 2 and the ceiling is 20, add a no-progress detector.
  • Defence in depth (token, cost); tune per task class.
3.5No-progress detector vs budget?Wasted vs absolute.
A budget caps absolute consumption; the detector caps wasted effort by counting consecutive iterations with no new information, then forcing BLOCKED. It fires earlier, on the pathology that matters most. Progress = the verifier's output or failing-test set changing.
3.6When to recurse (spawn a sub-agent) vs iterate in place?Independence and fresh context.
Recurse for a genuinely independent sub-task that benefits from a fresh context, its own budget and its own termination. Iterate when steps are tightly coupled and share state that is expensive to pass down. Anti-pattern: recursing for trivially coupled steps.
3.7Nested-loop structure of a production agent, and why it recurs?Different timescales.
An outer planning loop (what) wraps an inner tool-execution loop (how). Each layer has its own timescale and termination signal: "this tool call succeeded" vs "the overall goal is verified". One shared budget makes the system stop too eagerly or never.
3.8Crash mid-iteration; restart repeats a side effect. Fix?State + idempotency.
  • Serialise state at every iteration boundary.
  • Make side effects idempotent: key by a deterministic request id.
  • Define a resumption protocol that rebuilds working memory from saved state.
3.9Make a destructive-action guard impossible to bypass?Before dispatch, fail-closed.
Check it on every tool call before dispatch; fail closed; require specific, per-action approval recorded out of band in scratchpad["human_approved"], which only a human step can write. Never a guard that logs and proceeds, or one the model satisfies by saying "I have approval".
3.10What does early exit add, and when is it wrong?Verified signals only.
It saves cost and latency when continuing is provably pointless. It's dangerous when the "proof" is the model's own unverified claim. Exit on a checker passing or a deterministic precondition failing, never on self-assessment alone.

12Chapter summary

  1. Define success conditions, failure conditions and escalation paths before writing the loop's action logic.
  2. Design four stopping-rule guards deliberately: destructive-action, scope-creep, blocker escalation, unrelated-change.
  3. Budgets (token, time, tool-call, cost) are hard ceilings; exhausting one without progress means change strategy.
  4. Loops nest: an outer planning loop contains an inner tool-execution loop, at every scale.
  5. Long-running loops need durable, resumable state so a crash forces neither a restart from zero nor a repeated side effect.
