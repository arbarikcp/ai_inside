From Prompting to Looping

The unit of work is no longer the prompt; it is the loop. Stop prompting the agent turn by turn and build the system that prompts it.

01Chapter in 60 seconds

BeforeHolding the tool: write a prompt, read the reply, type the next instruction.
→
NowBuilding the system that holds the tool, then letting it drive the agent.
Definition · Loop engineeringThe discipline of designing, operating and improving the iterative cycles that let an AI system pursue a goal across multiple steps, rather than produce a single response. A loop engineer builds the system that prompts the agent, instead of prompting the agent directly.

What that system does, every iteration:

finds the work→hands it to the agent→checks the result→records what was done→decides the next action
  • Skill shift: phrasing a request well → designing a system that pursues a goal, reads the consequences of its own actions, and corrects course with no human retyping.
  • Abstraction moves up one level: from authoring prompts to authoring the loop that authors prompts.

02Why one-shot prompting hits a ceiling

A single response cannot run itself, test itself, notice it was wrong, and try again.

Key insight

A strong first answer is not the same as a correct final change. Loop engineering makes post-action signals part of the system instead of after-the-fact cleanup.

03Chain vs loop

ChainLoop
DefinitionFixed linear sequence A → B → C, run in a set order regardless of intermediate resultsRepeating cycle: each iteration's outcome decides whether and how the next one runs
StrengthPredictable, easy to trace, cheapFlexible; recovers from a wrong assumption
Best forWell-understood, low-uncertainty tasksPath unknown in advance: an unfamiliar error, an undocumented API, a partly visible codebase
Can change course?NoYes: accept, retry differently, or stop
Pitfall

A chain cannot recover from a wrong assumption at step one. It faithfully runs steps two through ten on a broken foundation. That confidently wrong output is the most common reason teams move to loops.

Rule

Pick the cheapest structure that meets the reliability bar. Start with a chain; add loops exactly where uncertainty and recoverable failure live.

04Five-stage anatomy of every loop

SignalRead it as
Test failureNew context the model did not have before
Type errorProof that an assumption was wrong
Review commentAnother observation that drives the next action

Mnemonic  I · C · A · O · A — Intent, Context, Action, Observation, Adjustment.

05Prompt engineering vs loop engineering

They are complementary. Prompt engineering shapes the input to a model; loop engineering shapes the entire process around it.

DimensionPrompt engineeringLoop engineering
Primary unitA prompt or instructionA repeated workflow
GoalBetter first responseBetter final outcome
FeedbackUsually human evaluationTests, tools, diffs, logs, reviews and humans
Failure modeThe model gives a weak answerThe system loops poorly, stops early, or ignores evidence
Best forIsolated answers and generationReal tasks with uncertainty
Reflex when attempt 1 failsWrite a better promptAdd a verifier and feed the failure back

Prompts still matter inside the loop: they shape the first plan, cut exploration and iteration count, and improve tool-call arguments. They stop being the top-level control surface.

06Why coding first, and where the idea comes from

DomainVerification signalLoop fit
CodingCompile, type-check, lint, test: dense, cheap, automatic, machine-readableStrong: matured here first
Customer support"Was the customer satisfied?": sparse, subjective, slow, expensiveWeak
Rule

A loop is only as good as its verification signal's quality and latency. First design question: what is my cheap, automatic verifier? If the honest answer is "a human reads it", the loop will be slow and expensive.

From the field

Anyone who built a CI/CD pipeline with automatic retries, or a robotics control loop, has done a version of this. What changed is the actor inside the loop.

07The five stages in code

The book's repo encodes the anatomy as an explicit, serialisable state machine. Every transition is recorded so a run can be replayed.

class LoopPhase(str, Enum):
    PLANNING       = "planning"        # Intent
    GATHER_CONTEXT = "gather_context"  # Context
    REASONING      = "reasoning"       # decide the next move
    ACTING         = "acting"          # Action
    OBSERVING      = "observing"       # Observation
    VERIFYING      = "verifying"       # Adjustment
    SUCCEEDED, BLOCKED, FAILED          # terminal: few and explicit
  • Adjustment is a first-class phase, not an afterthought. A chain has no OBSERVING or VERIFYING state.
  • "Plausible code" vs "the change actually works" is exactly the OBSERVING → REASONING edge on a failing test.
  • AgentLoop.run calls verify before moving to SUCCEEDED; a failure goes back as a new user message.
Cycle test

Draw your system as a directed graph. If it has no cycle, it is a chain, however many LLM calls it contains. Loop engineering begins the moment an observation can send control backward.

08Production lens: the same ideas in LangGraph not from the book

A bridge from the chapter to the framework in your study plan.

def route(state):               # the back-edge that makes it a loop
    if state["verified"]:
        return END
    if state["attempts"] >= 5:
        return "blocked"
    return "reason"              # failure reason already in state["messages"]

g.add_conditional_edges("verify", route, ["reason", "blocked", END])

09Self-test: exercises 1.1–1.10

Answer aloud first, then open the card.

1.1Loop engineering vs prompt engineering?What does each optimise?
  • PE optimises one input → output exchange: a better first response.
  • LE optimises the process around the model: finding work, assembling context, verifying, feeding failures back, stopping.
  • PE fails with a weak answer; LE fails by stopping early, ignoring evidence or burning budget.
1.2Chain vs loop, with a production example?Can an early error be detected and reversed?
OCR → summarise → email is a chain: bad OCR flows downstream. Add a verifier (character confidence, perplexity) and a back-edge that retries OCR with another engine or a deskew pass. Now step 1 can be reversed.
1.3The five stages, and which one carries the value?Trick question.
Intent, Context, Action, Observation, Adjustment. No single stage: the value is in closing the loop, so the next action is conditioned on the last signal.
1.4Why did loops mature in coding before customer support?Which domain has a cheap verifier?
Code self-verifies (compile, type-check, lint, test): dense, cheap, automatic, trustworthy. Support's signal is sparse, subjective and late. Loop feasibility = quality × latency of the verifier.
1.5"We have a multi-step LangChain pipeline, so we do loop engineering." Reply?Look for a feedback edge.
Ask whether any output can send control backward. Most pipelines are DAGs: sophisticated chains. Many steps is necessary, not sufficient; you need a back-edge gated by an observation.
1.6Intellectual lineage, and what is genuinely new?Three sources, one new fact.
OODA, ReAct, plan-act-verify. New: one LLM can be planner, actor and verifier inside one system, collapsing three subsystems (often three teams) into one loop.
1.7A loop gives confidently wrong output and never errors. Where do you look first?What can contradict the model?
Observation and Adjustment: a missing or ignored verifier. Classic bug: termination keys off "model gave a final answer" instead of "verifier passed". Make success depend on the verifier.
1.8When is a chain right and a loop wrong?Cheapest structure that meets the bar.
Well-understood, low-uncertainty tasks where each step succeeds given valid input: a known JSON into an email template, a fixed nightly report. A loop only adds calls, latency and non-determinism.
1.9How do you prove that moving chain → loop helped?Not by feel.
  • Fixed offline eval set.
  • Quality: success rate, pass@1. Cost: tokens, $, wall-clock. Reliability: variance, confidently-wrong rate, escalations.
  • Headline metric: cost per successful task. Also watch the iteration-count distribution: all 1s = overkill; many at the ceiling = weak verifier or action space.
1.10Where does prompt engineering still matter?Inside the loop.
Everywhere inside the loop: fewer iterations, better-formed tool-call arguments, better self-reports (which become observations). Tune the architecture first, the prompt second.

10Chapter summary

  1. Loop engineering designs the system that prompts the agent; it is not the act of prompting.
  2. A loop differs from a chain in one way: the outcome of an iteration changes what happens next.
  3. Every loop has five stages: Intent, Context, Action, Observation, Adjustment.
  4. Prompt engineering optimises one input; loop engineering optimises the system around repeated inputs and outputs.
  5. Coding led because code self-verifies through tests, compilers and runtime behaviour.
